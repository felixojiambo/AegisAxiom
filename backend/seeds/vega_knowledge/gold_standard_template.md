# Vega Knowledge Base — Gold Standard Discovery Report Template

**Source:** Bree's AEGISAXIOM Ecosystem deep research doc, "The Gold Standard Discovery Report" section, cross-referenced with the data model in `vega_design_doc_v2.md` section 4.
**Purpose:** This file defines what Vega's final output looks like at the end of the 3-call discovery process. It is the contract between Vega and Orion — when Orion receives a session via handoff, it expects every workflow in the matrix to conform to this template. Vega self-checks against this template before offering the Orion handoff at the end of Call 3.

---

## What the Gold Standard report is

The Gold Standard discovery report is the deliverable that justifies the entire 3-call process. Without it, the calls produced conversation but no artifact. With it, the rep walks away with a structured engineering blueprint that can be handed to Orion for SOW drafting, to deployment engineers for build planning, and to executive stakeholders for prioritization decisions.

The report is **NOT** a narrative summary. It is **NOT** a list of action items. It is a structured database of validated workflows, each one tagged, scored, and visually mapped. The report consists of two primary artifacts:

1. **The AI Employee Spreadsheet Matrix** — the master manifest of every identified workflow.
2. **Visual Process Flows in BPMN 2.0** — one diagram per workflow, showing the exact sequence of human, AI, and system actions.

Both artifacts must be present for the report to be considered complete. A matrix without diagrams leaves engineers without an executable blueprint. Diagrams without a matrix leave executives without a prioritization framework.

## Artifact 1: The AI Employee Spreadsheet Matrix

### Purpose

The matrix serves as the master manifest for the client's future digital workforce. It provides executive leadership with a clear, prioritized roadmap for automation. Every row represents a workflow that has been verified through the discovery process and is ready to be implemented as an AI Employee.

### Required fields per row

Each row in the matrix represents one workflow / proposed AI Employee. The field schema below mirrors the `ai_employee_matrix` structure in `vega_discovery_sessions` (see `vega_design_doc_v2.md` section 4 for the canonical Pydantic shape). Vega must populate all required fields before considering a workflow "matrix-complete."

| Field | Required? | Notes |
|---|---|---|
| `workflow_id` | Yes | Stable ID generated by Vega. Used by the BPMN tool, the matrix UI, and Orion to reference this workflow consistently. Never use array indices. |
| `workflow_name` | Yes | The proposed name of the AI Employee that will own this workflow. Examples from existing AEGISAXIOM agents: "Orion — SOW Builder," "Zenith — Financial Forecaster," "Pulsar — Rules Engine." When Vega generates names, use a similar format: a single-word persona name plus a role descriptor. |
| `description` | Yes | A one-paragraph description of the operational mandate. Should answer: what does this AI Employee do, when does it run, what does it produce? Avoid vague language. "Processes invoices" is wrong. "Cross-references vendor invoices against PO line items in QuickBooks daily, flags mismatches, and emails a daily exception report to the AP supervisor" is right. |
| `source_apps` | Yes | List of named applications the AI Employee will interact with. Use specific names from the discovery transcripts (QuickBooks, not "accounting software"). |
| `data_state` | Yes | One of: `blind`, `siloed`, `visible`. Vega's classification based on the Data State Diagnostic from the curriculum modules. |
| `data_state_justification` | Yes | A specific quote or paraphrase from the discovery transcripts supporting the data state classification. Vega cannot leave this field empty — if there's no justification, the classification is a guess and should be flagged as low-confidence. |
| `manual_hours_per_week` | Yes | Numeric estimate of how many hours of human labor this workflow currently consumes per week, totaled across all involved people. Source: explicit mentions in the transcripts. If not explicitly mentioned, mark as `null` and add to `needs_client_input`. |
| `stakeholders` | Yes | List of named stakeholders and their roles. Mirrors the `stakeholders_mentioned` field from the Call 1 analysis. |
| `actors` | Yes | List of actors with type classification (`human`, `ai`, `external_system`, `output`). This is what feeds the BPMN diagram's lanes. Required for BPMN generation. |
| `trigger` | Yes | The Call 2 trigger answer, structured: `{type, description, actor_id}`. Required for BPMN generation. |
| `steps` | Yes | Ordered list of steps with actor assignments and BPMN task type mapping. Required for BPMN generation. |
| `decision_points` | Optional | Decision gateways and their branch conditions. Optional only because some simple workflows have no decisions. If decisions exist in the workflow, they MUST be specified — undocumented decisions are not allowed. |
| `exception_paths` | Optional | Same logic as decision_points. Optional only if no exceptions exist. |
| `mmi_hypothesis` | Yes | The full per-dimension MMI structure with confidence flags. See the MMI section below. |
| `bpmn_xml` | Yes | The generated BPMN 2.0 XML for this workflow. Populated by the `generate_bpmn_diagram` tool. |
| `bpmn_status` | Yes | One of: `not_generated`, `generating`, `generated`, `failed`. Used by the matrix UI to show progress. |

### MMI hypothesis structure

The MMI score for each workflow is computed at the end of Call 3 using the formula `(TSS / IE) * (Time + Cost + Quality + Satisfaction)`, but the inputs (TSS, IE, and the four sub-dimensions) are populated incrementally across Calls 1, 2, and 3 with confidence flags per dimension.

For each of the six dimensions, Vega records:
- `value` — integer 1-5
- `confidence` — `high` / `medium` / `low`
- `reasoning` — a sentence or two explaining what Vega observed in the transcripts that led to this value

If `confidence` is `low`, the dimension goes into the workflow's `needs_client_input` list. This list tells the SE (and the matrix UI) which dimensions need to be reviewed with the client before the score is finalized. Yellow-highlighted cells in the matrix UI map directly to entries in `needs_client_input`.

**Vega must never set a value without recording reasoning.** Every dimension's `reasoning` field is required, even when confidence is high. This is the audit trail that lets the SE understand and trust Vega's hypothesis.

### Validation rules — when is the matrix "complete"?

Before Vega offers the Orion handoff at the end of Call 3, the matrix must pass these checks:

1. Every workflow has all required fields populated.
2. Every workflow has either an empty `needs_client_input` list, or has `needs_client_input` items that the rep has explicitly chosen to defer (with a note explaining why).
3. Every workflow has `bpmn_status: generated` (or has been explicitly marked as "diagram deferred" by the rep — some workflows are too simple or too vague to diagram and the rep can override).
4. Every workflow has a final MMI `score` populated (computed by `compute_mmi_score`).
5. There are no contradictions across workflows (e.g., two workflows can't both claim to be the system of record for the same data).

If any check fails, Vega must NOT offer the Orion handoff. Instead, Vega tells the user what's missing and proposes either a follow-up call or specific edits the rep can make to the matrix to close the gaps.

### What "good" looks like — example matrix entry

This is what a matrix-complete workflow entry should look like (abbreviated for readability):

```
workflow_id: wf_invoice_xref
workflow_name: "Orion Jr — Invoice Cross-Reference Specialist"
description: "Daily automated cross-referencing of vendor invoices against PO line items
              in QuickBooks. Flags discrepancies and emails an exception report to the
              AP supervisor each morning at 9am, replacing 4 hours/day of manual work
              currently performed by two AP clerks."
source_apps: [QuickBooks, Excel, Outlook]
data_state: siloed
data_state_justification: "Client confirmed in Call 1 that invoice data lives in QuickBooks
                          while PO tracking is maintained in a separate Excel workbook on
                          a shared drive. No integration exists between the two."
manual_hours_per_week: 20
stakeholders: [Sarah Chen (Finance Manager), Marcus Rodriguez (AP Clerk), Lisa Park (AP Clerk)]
actors:
  - {id: a1, name: "AP Clerk", type: human}
  - {id: a2, name: "QuickBooks", type: external_system}
  - {id: a3, name: "Excel PO Tracker", type: external_system}
  - {id: a4, name: "AP Supervisor", type: human}
trigger:
  type: scheduled
  description: "Daily at 8am, batch processing of all invoices received in the prior 24 hours"
  actor_id: a1
steps: [... ordered list ...]
decision_points: [... gateways ...]
exception_paths: [... boundary events ...]
mmi_hypothesis:
  tss: {value: 4, confidence: high, reasoning: "Client explicitly stated 4 hours/day of manual labor across two clerks"}
  ie: {value: 2, confidence: high, reasoning: "QuickBooks has a documented REST API; Excel can be read via standard libraries"}
  time: {value: 4, confidence: medium, reasoning: "Implied from Call 1 frustration about delays in catching mismatches"}
  cost: {value: 3, confidence: low, reasoning: "Fully-loaded labor cost not discussed; AP clerk salary range estimated"}
  quality: {value: 4, confidence: high, reasoning: "Client mentioned 'we miss things weekly' and 'audit findings last quarter'"}
  satisfaction: {value: 3, confidence: low, reasoning: "Not explicitly discussed; inferred from frustration tone"}
  needs_client_input: [cost, satisfaction]
  score: 28
bpmn_xml: "<bpmn:definitions>...</bpmn:definitions>"
bpmn_status: generated
```

This is a fully matrix-complete workflow. Notice that `cost` and `satisfaction` are flagged as `needs_client_input` — the matrix is still considered complete because the rep can either accept Vega's hypothesis values, edit them, or defer them with an explicit note. What matters is that Vega has been honest about its confidence.

## Artifact 2: Visual Process Flows (BPMN 2.0)

### Purpose

To ensure alignment between business stakeholders and technical deployment teams, every matrix-complete workflow must have a corresponding BPMN 2.0 diagram. These diagrams serve three audiences:

1. **The client** — visual confirmation that Vega understood the workflow correctly. Easier to spot errors in a diagram than in a textual description.
2. **The deployment engineers** — mathematically rigorous specification that can be translated directly into code.
3. **Executive stakeholders** — non-technical visualization of where AI fits into existing operations.

### Required elements per diagram

Every BPMN diagram for a matrix-complete workflow must define:

1. **The actors as lanes.** Use the `actors` array from the matrix entry to define lanes. Human actors, AI actors, and external system actors get their own lanes within a single pool. This is the visual mechanism that makes human-vs-AI handoffs immediately obvious.
2. **The trigger as a Start Event.** The type of start event matches the trigger type (timer event for scheduled, message event for inbound message, etc.).
3. **Each step as a task element.** The task type maps from the matrix's step.task_type field:
   - `user` → `bpmn:userTask` (a human is doing the work)
   - `service` → `bpmn:serviceTask` (an automated system call)
   - `business_rule` → `bpmn:businessRuleTask` (an AI decision or rule evaluation)
   - `manual` → `bpmn:manualTask` (a physical action without system support)
4. **Decision points as gateways.** Use Exclusive Gateways for either/or decisions, Parallel Gateways for split-and-merge, Inclusive Gateways for conditional multi-branch.
5. **Exception paths as Boundary Events.** Attached to the affected task, with the exception flow leading to the recovery path or escalation.
6. **Outputs as End Events.** Every workflow must terminate. End Events should be labeled with the output description (e.g., "Mismatch report sent to AP supervisor").
7. **Sequence flows connecting everything.** The diagram must be fully connected — no orphaned tasks, no unreachable end events.

### What every diagram MUST visually demonstrate

Per Bree's deep research doc, the diagrams must define precisely:

- **Where human input is required** — visible as tasks in human actor lanes.
- **Where API calls are made to external systems** — visible as service tasks in external_system actor lanes.
- **Where the AI agent exercises autonomous decision-making** — visible as business_rule tasks in AI actor lanes, often immediately followed by gateways representing the decision branches.
- **What the ultimate output looks like** — visible as labeled End Events.

When a rep walks the client through the diagram in Call 3, they should be able to point at the diagram and say "this is where your team currently spends 4 hours a day, and here's where the AI Employee replaces that work." The diagram makes the value proposition tangible in a way the matrix alone cannot.

### Validation rules — when is a diagram "complete"?

1. The diagram is renderable in `bpmn-js` without warnings (validated by the BPMN service's pipeline before saving).
2. Every actor in the matrix entry has a corresponding lane.
3. Every step in the matrix entry has a corresponding task element in the correct lane.
4. Every decision_point has a corresponding gateway with branches matching the matrix entry's branch conditions.
5. Every exception_path has a corresponding boundary event.
6. The diagram has at least one Start Event and one End Event.
7. There are no orphaned elements or broken sequence flows.

The BPMN service handles validation 1-7 automatically. Vega's job is to ensure the input matrix entry has all the data the BPMN service needs. If validation fails, the BPMN service returns an error and Vega must surface it to the user — typically meaning the matrix entry needs more information before the diagram can be generated.

## Self-check: Vega's pre-handoff checklist

Before Vega offers the Orion handoff at the end of Call 3, it should run this self-check and tell the user the result. If any check fails, Vega does NOT offer the handoff — instead, Vega tells the user what's missing.

```
GOLD STANDARD REPORT — PRE-HANDOFF SELF-CHECK

[ ] All workflows in the matrix have required fields populated
[ ] All workflows have either resolved needs_client_input or explicit defer notes
[ ] All workflows have BPMN diagrams generated (or explicit "diagram deferred" notes)
[ ] All workflows have final MMI scores computed
[ ] No contradictions exist across workflows
[ ] At least one workflow exists (no point handing off an empty matrix)

If all checks pass: "The discovery report is ready for Orion. Want me to make the handoff?"
If any check fails: list the failures and propose the specific actions needed to close them.
```

This self-check is also what makes the "Looks like our call analysis is done, I'd recommend handing the next steps off to Orion" message in Vega's system prompt actually trustworthy. Without the self-check, Vega might offer the handoff when the matrix is incomplete, and Orion would receive a bad input — breaking the credibility of the whole pipeline.

## Why the Gold Standard report exists

This file is intentionally specific because the temptation in any AI discovery process is to produce vague summaries that feel impressive but can't actually drive engineering work. The Gold Standard format prevents that. Every field is required because every field is needed by someone downstream — Orion, the deployment engineers, the executive sponsor. If a field is missing, someone downstream is going to make assumptions that may not be correct.

The defensive prompting principle applies at the report level too: Vega should produce an INCOMPLETE report and explicitly flag what's missing rather than fill gaps with plausible-sounding fabrication. A report that says "we need a follow-up call to nail down the approval thresholds for two workflows" is more valuable than a report that invents the thresholds.

The Gold Standard format is what makes Vega worth using. Without it, Vega is just a transcript summarizer.
